# 运维手册

本文是故障处置的操作手册。每个场景给出**判据**（怎么确认是这个问题）、
**处置**（怎么修）与**验证**（怎么确认修好了）。先看判据再动手,不要凭症状猜。

---

## 场景 1:账号被大面积锁定

**现象**:一批用户反馈"账号已锁定",且锁定用户集中在同一时间窗内。

**判据**

1. 管理端「登录事件」按事件类型筛 `LOGIN_FAILURE`,看失败是否集中;
2. 查锁定标记:`EXISTS iam:<realmKey>:loginlock:<username>`;
3. 查计数:`GET iam:<realmKey>:loginfail:<username>`。

**处置**

- **误伤**(口令策略过严或脚本误触):调高该域的登录策略
  (`maxFailAttempts` / `failureWindowMinutes` / `lockDurationMinutes`),再逐个解锁:
  ```sql
  -- 解除锁定标记(计数键让它自然过期即可)
  DEL iam:<realmKey>:loginlock:<username>;
  ```
  管理端「用户 → 锁定/解锁」也可单个解锁。
- **撞库/喷洒**:确认来源 IP,查 `iam:<realmKey>:loginfailip:<ip>` 与
  `iam:<realmKey>:loginlockip:<ip>`;已在网关上封禁该 IP 的,同时把该域的
  `ipMaxFailAttempts` 调低。

**验证**:解锁后让该用户登录一次,应立即成功;失败计数归零。

## 场景 2:身份域签名密钥需要轮换

**场景**:密钥泄露风险、密钥使用年限到期、监管要求。

**处置**

1. 管理端「身份域 → 密钥轮换」,平台生成新密钥并立即生效;
2. 旧密钥**立刻退役**,但公钥继续在 JWKS 发布——已签发的令牌在自然过期前仍可验签;
3. 通知各接入方重新拉取 JWKS(建议接入方缓存 JWKS 时保留旧公钥一段时间)。

**注意**:轮换只影响**新签发**的令牌。要让存量令牌立刻失效,用「账号运维 → 全端下线」
(递增令牌版本),两者目的不同,不要混用。

**验证**:拉取 `/realms/<realmKey>/oauth2/jwks`,确认新密钥在列;用新签发的令牌访问 userinfo 正常。

## 场景 3:第三方身份提供方(IdP)故障

**现象**:三方登录用户反馈"第三方登录服务暂时不可用"。

**判据**

1. 平台侧日志出现 `身份提供方调用失败`(告警级别);
2. 登录事件里出现 `LOGIN_FAILURE` 且失败原因为 IdP 调用失败。

**处置**

- **平台侧无责**:外部 IdP 不可用时,平台返回 `IDP_UNAVAILABLE`(HTTP 502)而不是
  "系统内部错误",便于区分"平台故障"与"上游故障"——前者要告警,后者要找 IdP;
- **用户侧有退路**:登录页始终保留账号密码入口,用户可改用口令登录;
- **降级口径**:如某提供方长期不可用,管理端「身份提供方」停用它,
  登录页入口立即消失(停用只影响登录入口,已绑定的外部身份保留,恢复启用即可继续用)。

**验证**:IdP 恢复后,三方登录应重新可用;若曾改配置,注意客户端密钥等敏感项
**留空表示保持原值**,不必重新录入。

## 场景 4:主密钥遗失或更换

**现象**:日志出现"机密解密失败"。

**影响范围**:身份域签名私钥与身份提供方客户端密钥都无法解出——该域无法签发令牌,
该提供方无法登录。

**处置**

1. **有备份**:用旧主密钥启动,再按需轮换(密钥轮换会重新加密新私钥);
2. **无备份**:
   - 身份域:管理端「身份域 → 密钥轮换」生成新密钥对。旧令牌无法验签,需通知接入方重新登录;
   - 身份提供方:重新录入客户端密钥(客户端密钥在外部 IdP 侧可自助重置);
3. 换主密钥的正确顺序:**先在旧密钥下把机密重新加密落库,再改环境变量**——
   直接换环境变量会让存量密文全部解不开。

## 场景 5:Redis 故障

**现象**:平台启动失败或运行期大量 500。

**判据**:日志出现 Redis 连接异常;`/actuator/health` 的 `redis` 组件为 `DOWN`。

**处置**

1. Redis 是**强依赖**,没有降级路径:平台不提供进程内兜底存储
   (退化到内存会导致多实例间状态不一致,比直接不可用更危险);
2. 恢复 Redis 后平台自动重连,无需重启;
3. Redis 不可用期间,已签发的访问令牌因授权记录在 Redis 中而无法验签,
   接入方会收到 401——这是预期行为,不是新增故障。

**验证**:`/actuator/health` 返回 `UP`;用户可正常登录与换令牌。

## 场景 6:审计表膨胀

**现象**:审计表行数持续增长,查询变慢。

**判据**:`SELECT count(*) FROM iam_audit_log;`

**处置**

- 平台默认保留 **180 天**(`iam.audit.retention-days`),每日 03:30 按域清理并留痕;
- 需要更短留存:调 `iam.audit.retention-days`(注意合规要求,文档基线是 ≥ 6 个月);
- 需要更长留存:调大该值,或按域做归档(先导出再清理);
- 导出:管理端「审计日志 → 导出 CSV」,或调 `GET /api/v1/admin/audit-logs/export`(独立权限码 `audit:export`)。

**注意**:审计表由数据库触发器保护,**任何 UPDATE/DELETE 都会被拒绝**。
留存期清理是唯一例外,且必须由平台在事务内打开清理通道后执行。
需要人工订正时,不要直接改表——补一条新记录说明情况更符合审计语义。

## 场景 7:用户反馈"总是被登出"

**判据**

1. 用户是否集中在某个实例上?→ 检查负载均衡是否指向了未共享 Redis 的实例;
2. 查会话键:`EXISTS iam:session:<sid>`(sid 取自浏览器 `IAM_SESSION` Cookie);
3. 查该域的会话策略:最大存续时长与空闲超时是否被配得过短;
4. 查账号状态:账号被禁用/锁定、或执行过「全端下线」,会话会立即作废
   (这是设计行为,不是故障)。

**处置**

- 多实例各自连了本地 Redis → 统一指向同一个 Redis 实例/集群,重启各实例;
- 会话时长配得过短 → 调该域的 `ssoSessionMax` / `ssoSessionIdle`;
- 账号被误禁用 → 管理端恢复账号状态。

**验证**:登录后连续访问若干页面,会话保持;跨实例访问(通过负载均衡连续请求)不掉登录态。

## 场景 8:应用门户点卡片进不去应用

**判据**:门户点卡片后看浏览器落到哪里,以及卡片上是否有「不可进入」角标。

| 现象 | 含义 | 处置 |
|---|---|---|
| 直接进入应用首页 | 正常 | — |
| 进应用后要求登录一次 | 应用没在入口路由之前发起授权 | 应用侧改:无会话时先 302 到 `/authorize` 再渲染 |
| 卡片标「不可进入」,点击退回门户 | 应用未配入口地址 | 「应用门户」补 `entryUrl` |
| 卡片列表里没有该应用,旧页面点进去退回门户 | 应用已停用或对当前用户不可见 | 检查 `enabled`、可见性与登录账号所属域 |

**常见原因**

1. **应用未配置入口地址** → 「应用门户」补 `entryUrl`,须 `http(s)` 开头;
2. **应用已停用** → 重新启用,或确认该应用应下线;
3. **用户看不到卡片** → 可见性(`PUBLIC` / `ROLE` / `PERMISSION`)与授权名单不匹配,
   不是启动链路的问题。停用与不可见对用户是同一个回答,不会暴露"这个应用存在"。

门户不参与拼授权地址,所以「点进去先报未登录」这类现象一律在应用侧排查:
`state` / `nonce` / PKCE 的生成与校验都在应用,门户只负责 302 到入口。

**验证**:门户点卡片 → 浏览器直接进入应用,全程没有第二次登录页。

### 场景 8.1:跳到 `/realms/{realm}/oauth2/authorize` 后 400

**判据**:浏览器停在 IAM 的错误页(「请求参数不被接受」),地址栏还是 `.../oauth2/authorize?...`。
`authorize` 返回 400 只代表**这次授权请求本身不合法**,与账号、密码、会话都无关,所以不要去看登录日志。

**最快的定位方式**是拿同一个请求只换一个变量逐项试,看 400 是否会变回 `302 → /login`
(`302 /login` 说明这一组参数已被接受,只是还没登录):

```bash
BASE='https://sso.example.com/realms/default/oauth2/authorize?response_type=code&client_id=<客户端>&scope=openid%20profile&state=x&nonce=n'
# 只换 redirect_uri,逐个试:https / http / 少一层路径 / 末尾带不带斜杠
curl -sS -o /dev/null -w '%{http_code} %{redirect_url}\n' "$BASE&redirect_uri=https://app.example.com/login/oauth2/code/iam"
```

| 命中项 | 结论 | 处置 |
|---|---|---|
| 只有某个 `redirect_uri` 变体返回 302 | 注册值与实际发出值不一致(最常见是 `http` vs `https`) | 二选一:①应用侧修 `{baseUrl}` 推导;②把实际地址**逐字**加进客户端回调白名单 |
| 所有变体都 400 | 客户端标识、作用域或 PKCE 参数不对 | 核对 `client_id` 是否属于该域、`scope` 是否已在客户端允许、公开客户端是否强制 PKCE |
| 403 而非 400 | 授权闸门拒绝(用户无权访问该应用) | 走「应用门户」补授权名单,见场景 8 |

**`http` vs `https` 的产生机理**:Spring 的 `{baseUrl}` 取的是它自己看到的请求协议。
TLS 在反向代理终结时,若代理没传 `X-Forwarded-Proto`、或应用没开
`server.forward-headers-strategy=framework`,后端会认为自己是 `http`,
于是发出去的 `redirect_uri=http://...`,而 IAM 里登记的是 `https://...`,字符串不等即拒。

> IAM 侧不会为"同一域名换个协议"放宽校验:回调地址是精确匹配的,不做归一化。
> 这是防开放重定向的底线,不要为了省事在 IAM 里同时登记 http 与 https 两个地址。

错误页对用户只给可行动的文案;真正的判定原因(OAuth2 的 `invalid_request` /
`invalid_redirect_uri` 等)随查询串一起打在 WARN 日志里,关键字:`请求被拒绝: status=400`。

### 场景 8.2:点卡片后浏览器在两个地址之间来回跳转

**现象**:点卡片后浏览器在应用首页与 IAM 授权端点之间反复跳转,地址栏停在应用首页并带
`?login_error=sso`,既不出现登录页也进不了业务页。

授权码每次都签发成功,失败发生在应用换取令牌这一步。链路:

```
应用首页 → /oauth2/authorization/iam → IAM 授权(已有会话,直接发码)
        → 应用回调 /login/oauth2/code/iam → 换令牌失败
        → 回跳应用首页 → 首页守卫判未登录 → 再发起授权 → 循环
```

**排查**:看应用侧日志,关键字 `IAM 登录回调失败`,其中 `error=` 即失败类型。

| `error` | 含义 | 处置 |
|---|---|---|
| `invalid_client` | 客户端密钥与 IAM 登记值不一致(常见于 IAM 重置密钥后未同步) | 同步应用配置,或重新 reset 一次密钥 |
| `invalid_grant` | 授权码已使用、已过期,或回调地址与授权时不一致 | 检查是否重复消费回调、回调地址是否被改写 |
| `invalid_state` | 回调时找不到对应的授权请求 | 多为跨主机名访问,`localhost` 与 `127.0.0.1` 的 Cookie 不互通 |
| `invalid_token` | 令牌验签失败 | 检查时钟偏差与 JWK 轮换 |

**确认客户端密钥是否生效**:用一个注定失败的授权码探路,不改任何配置。

```bash
# invalid_grant = 客户端认证通过;invalid_client = 密钥不对
curl -s -u "<client_id>:<client_secret>" \
  -d 'grant_type=authorization_code&code=bogus&redirect_uri=<登记的回调地址>' \
  https://<iam-host>/realms/<realm>/oauth2/token
```

**应用侧需要满足两点**,否则即使密钥正确也会打转:

1. 回调失败回跳到统一的认证入口页(如 `/auth/entry?login_error=sso`),不能回站点根路径,
   根路径的守卫只会判未登录并重新发起授权;
2. 失败原因写日志,框架默认的失败处理器只做 302,不记录异常。

**端口冲突**:若 `请求被拒绝` 日志里持续出现与本平台无关的路径(如 `/registry/machine`),
说明该端口上原本有别的服务。日志中的 `caller=` 可确认来源;把 IAM 换到其他宿主端口
(`IAM_PORT`,本地默认 8090)比逐条屏蔽更直接,依赖方 `issuer` 需同步修改。

### 场景 8.3:回调报 `invalid_user_info_response`(userinfo 401)

**现象**:应用日志 `invalid_user_info_response ... 401 Unauthorized: [no body]`。换令牌已成功,
失败在其后取用户信息这一步。`/userinfo` 返回 401 时响应体为空,这是协议规定,
排除方法看 IAM 侧 WARN 日志:

| 日志 | 含义 | 处置 |
|---|---|---|
| `Bearer 令牌被拒 ... 携带令牌=false` | 请求没带 Authorization,通常是代理丢头 | 检查代理是否透传 `Authorization` |
| `... detail=账号已禁用或锁定` / `令牌已因全端下线失效` / `令牌对应的账号不存在` | 令牌版本或账号状态失效 | 确认账号状态;重新登录取新令牌 |
| `... detail=ID Token 不能作为访问令牌使用` | 把 ID Token 当访问令牌用了 | 检查调用方取的令牌类型 |
| `令牌签发方与当前访问地址不一致: 期望=... 实际=...` | `iam.issuer-base-url` 未配置,令牌签发时的主机名与当前访问主机名不同 | 生产显式配置 `IAM_ISSUER_BASE_URL`;代理透传 `X-Forwarded-Proto` |

**判定要点**:`/userinfo` 的 401 与客户端密钥无关——密钥错会在换令牌那一步返回 `invalid_client`。
